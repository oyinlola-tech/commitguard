# Case study template

Copy into `evidence/case-studies/<name>.md` and fill in. Publish nothing without
written permission from the organization or project involved.

---

## Summary

One paragraph: who, what they run, what changed.

## Problem

What contribution-policy or provenance problem existed before CommitGuard? How
was it handled - by hand, by review, or not at all?

## Environment

| | |
|---|---|
| Repositories | number, size, language |
| Developers | number |
| Platform | GitHub.com / Enterprise |
| Deployment mode | local hooks / Actions / App |
| CommitGuard version | commit SHA |
| Dates | pilot start and end |

## Before CommitGuard

Any measurements taken before enforcement: how much AI attribution was already in
the history, how often it appeared, what review caught.

## Deployment

What was installed where, how long it took, and what went wrong during setup.

## Policy

Which rules, which actions, and why. Any exceptions granted, with scope and
expiry.

## Findings

| | Count |
|---|---|
| Commits scanned | |
| Violations found | |
| Confirmed false positives | |
| Known false negatives | |
| Exceptions requested / granted | |

## Remediation

What developers actually did when blocked, and how long it took.

## Performance

Hook overhead as experienced, scan latency, anything that felt slow.

## Developer feedback

Quotes, with permission. Include the critical ones - a case study with no
complaints is not credible.

## Outcome

What changed: policy, process, tooling. What was kept, what was dropped.

## Limitations

What this case study does **not** show: sample size, duration, the fact that
metadata can be removed, anything that was not measured.
