# Development guide for maintainers

Contributor basics (setup, tests, lint, commit rules) are in
[CONTRIBUTING.md](../../CONTRIBUTING.md). This page collects the recurring
maintenance tasks and the places where a change has to be made in more than
one file.

## Environment

```bash
./scripts/install-dev.sh && source .venv/bin/activate
commitguard doctor
```

- The `dev` extra includes `cryptography`, so App and dashboard tests run
  locally without extra steps.
- `web/` needs Node.js 20.19+; `npm run e2e` uses `../.venv/bin/python`.
- Tests isolate Git from your global configuration, so a local
  `core.hooksPath` or commit signing setting does not affect them.

## Full local check before merging

What CI runs, plus what CI does not run:

```bash
ruff check . && ruff format --check . && mypy
python -m pytest
pytest -m security
ruff check --select S,BLE . && bandit -r src -ll      # security workflow
COMMITGUARD_NETWORK_TESTS=1 pytest tests/integration/github/test_action_scripts.py   # needs PyPI
(cd web && npm ci && npm test && npm run typecheck && npm run lint && npm run build && npm run e2e)   # not in CI
```

## Recurring tasks

### Changing a runtime dependency

1. Discuss in an issue (policy: no new dependencies without discussion).
2. Update `pyproject.toml`.
3. Update the pins in `requirements/ci.in` and regenerate hashes (command in
   the file header):

   ```bash
   pip-compile --generate-hashes --allow-unsafe --strip-extras \
     --output-file requirements/ci.txt requirements/ci.in
   ```

4. Run `tests/integration/github/test_action_scripts.py` with
   `COMMITGUARD_NETWORK_TESTS=1`: the Action installs from `requirements/ci.txt`
   with `--require-hashes`.
5. Note it in `CHANGELOG.md`.

### Updating a pinned GitHub Action

Replace the full commit SHA and the tag comment together
(`uses: actions/checkout@<40-hex>  # vX.Y.Z`). Check the release notes of the
action for permission or behaviour changes.
`tests/unit/github/test_workflows_static.py` rejects unpinned references.
The same pins appear in `action.yml` and in the workflow template rendered by
`commitguard init --github` (`src/commitguard/github/workflow.py`).

### Changing hook scripts

Hook scripts are generated by `commitguard.git.hooks.render_hook_file`. The
reference copies in `hooks/` must match the generator exactly
(`tests/integration/hooks/test_hook_templates.py`). Regenerate them:

```bash
for hook in pre-commit commit-msg pre-push; do
  python -c "import sys; from commitguard.git.hooks import HookType, render_hook_file; sys.stdout.write(render_hook_file(HookType(sys.argv[1]), ''))" "$hook" > "hooks/$hook"
done
```

Keep them LF (`.gitattributes`). A change to the generated block makes
installed hooks report as outdated in `commitguard doctor`; say so in
`CHANGELOG.md` so users re-run `commitguard install`.

### Adding or changing rule data

- `rules/ai-identities.yaml`, `ai-domains.yaml`, `bot-identities.yaml`,
  `patterns.yaml` are validated strictly (`tests/unit/rules/`).
- An identity is `verified: true` only with a link to a public commit showing
  the attribution.
- Add dataset cases for the new identity in a **new dataset version**
  (`src/commitguard/research/datasets.py`), including near-miss human cases
  for false positives, then run `commitguard benchmark detection`.
- The rules version hash changes; scans record it.

### Adding a rule ID or policy

1. Detector emits the finding (detectors never decide).
2. Default policy in `src/commitguard/policies/defaults.py`, and the same
   entry in the `commitguard init` template
   (`src/commitguard/config/defaults.py`) and `config/default.yaml`. A test
   checks that `config/default.yaml` equals the template; no test checks that
   the template's actions equal `policies/defaults.py`, so compare them by
   hand.
3. Known policy IDs in configuration docs (`docs/configuration.md`,
   `docs/policy-engine.md`).
4. Dashboard labels if the rule is shown there (`web/src/lib/labels.ts`).

### Adding a CLI command or option

- Use `handled_errors()` and `ExitCode` from `src/commitguard/cli/output.py`;
  exit codes stay `0`/`1`/`2`.
- Sanitise every untrusted string before printing.
- Heavy imports (App service, storage, research) go inside the command
  function; the CLI import tests fail otherwise.
- Update `README.md` CLI usage and the relevant doc page.

### Changing the database schema

1. Append a new migration script to `_MIGRATIONS` in
   `src/commitguard/github/storage.py` and increment `SCHEMA_VERSION`. Never
   edit an existing migration.
2. Add a test that creates a database at the previous schema with data, opens
   it with `SqliteStateStore`, and checks the upgraded data (see
   `test_migration_from_schema_2_backfills_executions`).
3. Keep new tables tenant-scoped (installation or account IDs) and add them to
   retention purging if they grow without bound.
4. Describe the migration and its effect on existing data in `CHANGELOG.md` and
   in the upgrade section of the deployment documentation.

### Adding an API route

1. Route in `src/commitguard/api/` calling a control plane or governance
   service; no SQL in `api/` (architecture test).
2. A permission check for the route. `test_every_permission_is_checked_somewhere`
   checks that every permission is used.
3. Cross-tenant and role tests. Some sweeps enumerate the route tables
   automatically: `test_unauthenticated_requests_are_rejected` iterates every
   `/api/v1` route, and
   `test_other_tenants_get_not_found_for_every_governance_route` iterates every
   governance route (a new path placeholder needs a value in the `resources`
   fixture). Add explicit tests for role differences and for resources that
   belong to another tenant.
4. Document the route (`docs/dashboard.md` API reference and `docs/api/`).
5. Typed client in `web/src/api/` if the dashboard uses it.

### Adding a notification type

Notification types are the `NotificationType` enum in
`src/commitguard/notifications/models.py`. Follow an existing type through the
code (for example `policy_rollout_failed`) to find every place that needs an
entry, document the type in `docs/notifications.md`, and test deduplication
and delivery in test mode (`COMMITGUARD_NOTIFICATIONS_MODE=test`).

### Regenerating README evidence and images

```bash
python scripts/readme_evidence.py          # runs the suites and checks, writes docs/evidence/
cd web && npm run build && npm run screenshots
```

This runs the full test suites; do not run it on a machine that is recording
benchmarks. Commit the regenerated evidence together with the change it
describes, never hand-edited numbers.

### Recording benchmarks

See [benchmarking.md](benchmarking.md).

### Updating the changelog

`CHANGELOG.md` is maintained by hand in
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format. Entries go
under `## [Unreleased]`, grouped as `Added`, `Changed`, `Deprecated`,
`Removed`, `Fixed`, `Security` (existing entries also carry a phase in the
heading, for example `### Added (Phase 8 — ...)`). Write what changed for users
and operators, including effects on enforcement.

## Demo stack

```bash
cd web && npm ci && npm run build && cd ..
python tests/e2e/dashboard_harness.py --demo      # http://localhost:4173
```

The harness runs the real service against an offline model of GitHub and
records e-mail and webhook deliveries in memory. It is a test fixture, not a
deployment method.
